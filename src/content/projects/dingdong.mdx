## Overview

During my graduation internship at **Dingdong**, a housing platform for students and young professionals, I worked on the infrastructure connecting shared room listings to the mobile application. My responsibilities covered **backend APIs, a public Next.js web platform, and deep-link integration** in the existing Expo app.

The goal was straightforward for users: open a shared link, preview the room without installing anything, and continue to that same room in the app. Delivering that experience required changes across several systems, from room identifiers and public data access to link handling and mobile navigation.

## The Challenge

Dingdong already supported sharing links, but the journey was incomplete. Generated links did not consistently carry a room's `public_code`, so recipients could land on a generic app screen instead of the listing they expected. Deep-link context was held in memory and could be lost across app restarts. There was also **no public room preview**, meaning people were asked to install the app before seeing the room.

The challenge was to improve this flow **within the existing Django, Expo, and AppsFlyer stack**, while keeping the implementation maintainable and creating a foundation for measuring the web-to-app journey.

## Building the Web Platform

I developed a public room browsing and preview application with **Next.js**, deployed on **Cloudflare Workers**. It provides an overview of available rooms and a dedicated page for each listing, with room details, photos, and a call to action to open the mobile app.

Room data is fetched from the Django API, validated with **Zod**, and mapped into an internal model. For listings with incomplete media, the gallery falls back between room photos, group pictures, and house images, removing duplicates along the way. The interface also uses approximate map locations rather than exposing precise addresses.

Because these pages are shared outside the app, I implemented **Open Graph metadata** and search indexing rules so links produce useful previews and inactive listings are excluded from indexing.

## Backend & External Integrations

The web platform needed a reliable source of public room data. I developed a new **Django `integrations` application** that supports both the preview website and external partners.

The integration layer includes **API-key authentication**, management tools for partner keys, and separate serializers for different consumers. Public room responses expose the information needed to render a listing without returning sensitive details such as exact addresses or coordinates. Partner-facing responses support broader integration requirements.

I also implemented endpoints for retrieving a room by its `public_code` and for **bulk synchronization** with external services. While working with an external partner, I refined synchronization behavior and normalized timestamps to UTC to avoid inconsistent results across systems.

## Connecting Web and Mobile

The preview's **Open in app** action generates an **AppsFlyer OneLink** containing the room's `public_code`. For users with the app installed, Universal Links on iOS and App Links on Android connect the incoming link to the Expo application, where the existing `DeepLinkCoordinator` directs the user to the matching room. Routing accounts for both guest and authenticated users.

The installed-app flow was validated on iOS and Android.

I also worked on **persisting pending deep-link context with Expo SecureStore** so the room identifier can survive app restarts and onboarding transitions. This addressed a weakness in the previous in-memory approach.

The installed-app flow was validated on **iOS and Android**. A fresh-install journey was more difficult: the store redirect worked, but AppsFlyer did not reliably restore the original room identifier after installation during acceptance testing. Reopening the same link after installation did work.

As follow-up integration work, I added **Detour-related code and configuration** alongside AppsFlyer, including an incoming-link entry point and a bridge intended to feed the existing routing architecture. This work was handed over without claiming that the full Detour flow had been verified end to end on clean devices.

## Engineering Decisions

### Choosing the web framework

Rather than selecting a framework solely on familiarity, I benchmarked **Django templates, Next.js, and React Native Web** for the public preview layer. The comparison covered response time, load handling, page performance, and social-sharing metadata.

In the live-API benchmark, **Next.js with Incremental Static Regeneration (ISR)** handled **455 requests per second**, compared with **323** for Next.js without ISR and **7.72** for the tested Django implementation. These were results from a specific test setup, not general performance claims about the frameworks. Combined with complete Open Graph support and room-page rendering needs, the findings supported choosing Next.js.

### Keeping the system maintainable

I separated the public web layer, Django integrations API, and mobile routing responsibilities rather than combining them into one tightly coupled flow. The web application validates API responses at the boundary, while link providers feed into the app's existing coordination logic instead of requiring separate navigation systems.

### Deployment and verification

I configured **development and production Cloudflare Workers**, environment-specific settings, and a **GitHub Actions** pipeline with build and test checks. Testing covered backend authentication and responses, web interactions, missing images and invalid room identifiers, and mobile linking scenarios. I also resolved configuration issues involving build-time `NEXT_PUBLIC_` variables and OneLink destinations.

## Results & Reflection

The project delivered a **production webpreview platform**, a reusable **Django integrations API**, and a working **installed-app deep-link flow** on iOS and Android. During the reporting period, Cloudflare Analytics recorded **more than 11,000 visits** to the webpreview pages. That shows the pages were being accessed in production, but does not establish an increase in app installs or conversions.

Not every original objective was fully achieved. **Deferred deep linking after a fresh installation remained unresolved** in acceptance testing, and the desired end-to-end funnel measurements could not be fully validated with the available AppsFlyer plan. The later Detour integration work also required further device-level verification. I documented these limits and handed over the remaining integration work.

The most valuable lesson was that **cross-platform features succeed or fail at their boundaries**. A correct frontend, API, or mobile route is not enough on its own; identifiers, configuration, state, and installation behavior must remain consistent across the entire journey. This project strengthened how I investigate existing systems, justify architecture choices with evidence, and communicate unfinished work clearly.
